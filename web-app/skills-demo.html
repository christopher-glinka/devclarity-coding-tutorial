📌 Code to Explain

const fetchUserData = async (userId) => {
  const response = await fetch(`/api/users/${userId}`);
  const data = await response.json();
  const topPosts = data.posts.filter(post => post.likes > 10);
  return { ...data, topPosts };
};

fetchUserData(42).then(result => {
  document.getElementById('user-name').innerHTML = result.name;
});

🔍 AI Breakdown

Key Components:

  • fetchUserData() — Async function that calls an API and returns processed data
  • fetch() — Built-in browser API for making HTTP requests
  • response.json() — Converts the raw response into a JavaScript object
  • .filter() — Creates a new array with only posts that have more than 10 likes
  • { ...data, topPosts } — Spreads all original user data and adds the new topPosts property

How it runs step by step:

  1. Function is called with a user ID (e.g. 42)
  2. An HTTP GET request is made to /api/users/42
  3. The response body is parsed as JSON
  4. Posts with fewer than 10 likes are filtered out
  5. The result object is returned and rendered into the page

⚠️ Gotchas: Using innerHTML with user-supplied data is a security risk (XSS). Use textContent instead. Also, there is no error handling if the API request fails.

❌ Code with Issues

function searchUsers(query) {
  let results = [];
  for (let i = 0; i < allUsers.length; i++) {
    if (allUsers[i].name.includes(query)) {
      results.push(allUsers[i]);
    }
  }
  document.getElementById('results').innerHTML =
    '
    ' + results.map(u => '
  • ' + u.name + '
    • ').join('') + '
';
  return results;
}

🐛 Issues Found

Issue 1: Security — XSS Vulnerability Critical

User names from the API are inserted directly into innerHTML. An attacker could inject malicious HTML or JavaScript.

Fix: Build DOM elements with document.createElement and textContent.

Issue 2: Performance — Inefficient Loop Medium

A for loop with an index is more verbose and error-prone than a functional alternative. Use Array.filter() instead.

Issue 3: Accessibility — No ARIA Labels Medium

The results list has no context for screen readers. Add a role and aria-label so assistive technology can describe the results.

✅ Improved Code

function searchUsers(query) {
  const results = allUsers.filter(user =>
    user.name.toLowerCase().includes(query.toLowerCase())
  );

  const container = document.getElementById('results');
  container.innerHTML = '';

  const list = document.createElement('ul');
  list.setAttribute('role', 'list');
  list.setAttribute('aria-label', `Search results for "${query}"`);

  results.forEach(user => {
    const item = document.createElement('li');
    item.textContent = user.name; // Safe: no XSS risk
    list.appendChild(item);
  });

  container.appendChild(list);
  return results;
}

What it does: Analyzes how your system is structured, identifies design patterns in use, and recommends architectural improvements.

When to use: When designing a new feature, refactoring existing code, or onboarding to an unfamiliar codebase.

🏗️ Monolithic Approach (Before)

// Everything in one class — hard to test, hard to extend
class App {
  constructor() {
    this.users = [];
    this.posts = [];
    this.comments = [];
  }

  addUser(name) { /* user logic */ }
  getUser(id) { /* user logic */ }
  createPost(userId, content) { /* post logic */ }
  likePost(postId) { /* post logic */ }
  addComment(postId, text) { /* comment logic */ }
  validateEmail(email) { /* validation */ }
  formatDate(date) { /* formatting */ }
  sendNotification(userId, msg) { /* notifications */ }
  uploadImage(file) { /* file upload */ }
}

⚠️ Architectural Problems

  • Single Responsibility Violation: One class handles users, posts, comments, validation, formatting, notifications, and uploads.
  • Hard to Test: You can't test user logic without instantiating everything else.
  • Tight Coupling: All concerns are entangled — a change in one area risks breaking another.
  • Hard to Scale: Every new feature means modifying this one class.

✅ Modular Architecture (After)

// Separate services, each with one responsibility
class UserService {
  addUser(name) { /* user logic only */ }
  getUser(id) { /* user logic only */ }
}

class PostService {
  createPost(userId, content) { /* post logic only */ }
  likePost(postId) { /* post logic only */ }
}

class ValidationService {
  validateEmail(email) { /* validation only */ }
}

class NotificationService {
  send(userId, message) { /* notifications only */ }
}

// App wires services together — doesn't implement details
class App {
  constructor() {
    this.users = new UserService();
    this.posts = new PostService();
    this.validator = new ValidationService();
    this.notifications = new NotificationService();
  }
}

✨ Why This Is Better

Pattern Used: Service Layer + Dependency Injection

  • Each class has one job — easy to reason about and test in isolation
  • New features can be added without touching existing services
  • Services can be swapped out (e.g., for mocks in tests)
  • Aligns with the Open/Closed Principle: open for extension, closed for modification

🧪 Function to Test

function calculateDiscount(price, quantity, memberStatus) {
  if (price <= 0 || quantity <= 0) {
    throw new Error('Price and quantity must be positive');
  }

  let discount = 0;
  if (quantity >= 10) discount += 0.10;
  if (quantity >= 20) discount += 0.05;
  if (memberStatus === 'premium') discount += 0.15;

  return price * quantity * (1 - discount);
}

🗺️ Test Strategy

  • Happy paths: Basic price, quantity discounts, premium member discount, stacked discounts
  • Edge cases: Minimum quantity (1), decimal prices, exact threshold values (10, 20)
  • Error scenarios: Negative price, zero quantity, negative quantity

✅ Generated Test Suite

describe('calculateDiscount', () => {

  // Happy Path Tests
  it('should return full price when no discounts apply', () => {
    expect(calculateDiscount(100, 5, 'regular')).toBe(500);
  });

  it('should apply 10% discount for 10 or more items', () => {
    expect(calculateDiscount(100, 10, 'regular')).toBe(900);
  });

  it('should apply 15% discount for premium members', () => {
    expect(calculateDiscount(100, 5, 'premium')).toBe(425);
  });

  it('should stack quantity and member discounts', () => {
    // 10% (qty 20) + 5% (qty>=20) + 15% (premium) = 30% off
    expect(calculateDiscount(100, 20, 'premium')).toBe(1400);
  });

  // Edge Cases
  it('should handle minimum quantity of 1', () => {
    expect(calculateDiscount(100, 1, 'regular')).toBe(100);
  });

  it('should handle decimal prices correctly', () => {
    expect(calculateDiscount(9.99, 2, 'regular')).toBeCloseTo(19.98);
  });

  it('should apply extra 5% at exactly 20 items', () => {
    expect(calculateDiscount(100, 20, 'regular')).toBe(1700);
  });

  // Error Scenarios
  it('should throw when price is negative', () => {
    expect(() => calculateDiscount(-100, 5, 'regular'))
      .toThrow('Price and quantity must be positive');
  });

  it('should throw when quantity is zero', () => {
    expect(() => calculateDiscount(100, 0, 'regular'))
      .toThrow('Price and quantity must be positive');
  });

  it('should throw when quantity is negative', () => {
    expect(() => calculateDiscount(100, -3, 'regular'))
      .toThrow('Price and quantity must be positive');
  });
});

What it does: Identifies performance bottlenecks in your code, analyzes algorithmic complexity, and provides optimized alternatives with measurable improvements.

When to use: When your app feels slow, when processing large datasets, or when optimizing critical code paths.

🐌 Slow Implementation

// Find all duplicate values in an array
function findDuplicates(items) {
  const duplicates = [];
  for (let i = 0; i < items.length; i++) {
    for (let j = i + 1; j < items.length; j++) {
      if (items[i] === items[j] && !duplicates.includes(items[i])) {
        duplicates.push(items[i]);
      }
    }
  }
  return duplicates;
}

// 1,000 items → ~500,000 comparisons
// 10,000 items → ~50,000,000 comparisons

⚠️ Performance Issues Found

Issue 1: O(n²) Nested Loops Critical

For every item, the inner loop checks every other item. At 10,000 items this means 50 million comparisons.

Issue 2: .includes() Inside Inner Loop Critical

duplicates.includes() is itself O(n), making the true complexity O(n³). Every comparison triggers another full scan.

⚡ Optimized Implementation

// Find all duplicate values in an array — O(n)
function findDuplicates(items) {
  const seen = new Set();
  const duplicates = new Set();

  for (const item of items) {
    if (seen.has(item)) {
      duplicates.add(item); // Set.add() ignores duplicates automatically
    } else {
      seen.add(item);
    }
  }

  return Array.from(duplicates);
}

// 1,000 items → ~1,000 operations
// 10,000 items → ~10,000 operations

📊 Performance Comparison

Metric Before After Improvement
Time Complexity O(n³) O(n) Cubic → Linear ✅
1,000 items ~500M ops ~1,000 ops 500,000× faster ✅
10,000 items ~50B ops ~10,000 ops 5,000,000× faster ✅
Memory O(n) O(n) Same

Key Insight: Set.has() is O(1) — it checks membership in constant time regardless of size. Replacing nested loops with a single pass over a Set transforms an unusable algorithm into a fast one.
